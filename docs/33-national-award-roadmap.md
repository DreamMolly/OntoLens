v0.3.0 保留为本地候选。按 2026-10-08 最新要求，实际应用与完整参赛展示未通过验收前，不创建新远端仓库或推送源码。当前源码、README 与里程碑交接可以在本地检查；完成本地测试不解除发布条件。

5. 在有用途授权和领域核对的资料上完成旁路任务与独立效果评测，再复核参赛展示和发布条件。

## 优先级与完成门槛

### P0：先把安全边界做成可审计证据

1. 修复并测试所有跨版本证据引用，尤其是关系图中的规则版本、快照哈希和来源闭包。（已完成首个跨版本回归）
2. 增加针对单位、数量边界、未知实体、过期/破损批次和冲突类别的变形测试；每个测试同时检查 `decision`、`reason_code`、批准数量和 `needs_review` 行为。（已完成21个合成变形案例，包含授权与批次边界；仍需扩展真实资料评测）
3. 为每个拒绝、隔离和复核结果生成可读的“最小证据链”：输入事实、触发规则、未满足条件、人工下一步和不可推断的部分。

门槛：新增测试全部通过；任何模型或检索输出都不能改变程序决定；导出包能离线重算来源哈希。

### P1：把评测从一个数字扩展为可质询的对照

1. 保持回归、事故、留出三套数据隔离；增加按动作、理由码、数量边界和风险等级的分层统计。（已完成结构化报告）
2. 对每次规则变更生成“基线→候选→留出”的差异报告，列出安全释放、过度拦截、限量误差和失败案例。
3. 增加合成扰动与反事实测试，例如只改变单位、库存、柜位或当天未归还类别，确认决定只因该事实变化而变化。（已完成21个合成案例）
4. 对任何新指标记录数据来源、样本构造、版本、运行时间和限制；不把合成集的 60/60 写成行业准确率。

门槛：每次候选规则发布都有机器可读报告；v2 gate 继续通过；v3 若失败，报告必须解释失败原因和是否属于预期教学示例。

### P2：把人工复核做成真正的工作流

1. `needs_review` 项目显示缺失证据、冲突证据、过期证据和建议补件，而不是只显示一个状态词。（已接入工作台）
2. 增加审核意见、证据引用和复核时间的结构化记录；审核人未提供时明确显示“未完成”。（已支持追加记录并保留原决定）
3. 上传资料先进入待审来源层；只有来源授权、定位、快照绑定和人工确认齐备才允许进入候选版本。

门槛：复核记录可导出、可回放、可追溯到原始字节；任何缺证据项都不会生成业务决定。

### P3：准备真实资料接入和独立复核

先实现受控台账导入和待审快照，不以缺少内部资料为由停止工程建设。进入真实场景验收前仍需用途授权的脱敏资料、领域审核、真实历史旁路任务、独立冷启动环境、费用/调用上限和持续负载预算。接入时保留原文件哈希、授权范围、撤回方式和专业审核意见；公开政策采集不能替代真实库存与人员授权。

门槛：真实资料与合成资料分开存储；独立复核人能按 README 从空环境复现；结果至少报告安全释放、过度拦截、漏检、延迟、成本和失败日志。

### P4：答辩和材料收口

1. 演示顺序固定为：同一申请的四种程序决定 → 缺证据进入 `needs_review` → 证据定位 → 候选变更预览 → 发布/回滚 → 导出复现包。
2. 每页材料只保留一个主结论和一个可复核命令；所有数字绑定到报告路径和日期。
3. 准备失败演示：错误单位、未知人员、冲突类别、过期批次、模型不可用、Docker 不可达和引用未解决。

门槛：Word/PPT/演示脚本/证据矩阵中的数字、哈希和边界一致；评委不需要相信口头承诺才能复核关键结论。

## 每轮迭代规则

- 先读取最新 `local-validation-report.json`、`deliverable-consistency-report.json`、模型就绪报告和证据矩阵，再决定下一项工作。
- 发现外部前置条件未满足时，转向可在本地完成的 P0/P1/P2 工作，不伪造真实资料结果。
- 代码变更必须带有针对性测试；材料变更必须重新做结构/视觉检查；证据变更必须有独立校验报告。
- 一轮完成后更新本文件的日期、改动、验证命令、风险和下一步；若证据退化，优先修复证据链而不是增加新功能。
